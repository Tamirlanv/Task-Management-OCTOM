## Функциональность и качество

- 104 unit/integration-теста прошли на Python 3.12.14, PostgreSQL 18 и Redis 8.2.
- Покрытие строк `app/`: 99,94% (1 782 из 1 783 строк), порог — 80%.
- Ruff, Black и строгий mypy прошли; lock-файл проверен в offline-режиме.
- Проверены auth, истечение и абсолютный срок refresh-сессий, хранение только хешей, replay и конкурентное обновление, все роли, межтенантная изоляция, защита последнего Admin, снятие назначений, CRUD, фильтры, каскадные удаления, rollback, rate limit и отказ Redis.
- Составные FK проверены прямыми некорректными SQL-вставками, отдельно от сервисной валидации. Проверены миграции с пустой схемы и обновление первой ревизии до второй; `alembic check` не обнаружил расхождений с ORM.
- Контейнерный запуск API, миграций, PostgreSQL и Redis прошёл. `/docs`, `/openapi.json`, оба health-маршрута и `/metrics` отвечают `200`.

Отдельный отчёт ветвлений сформирован для набора из 100 тестов перед добавлением четырёх дополнительных проверок сессий. На Python 3.12 coverage использовал запасной tracer: отчёт показывает 67,74% ветвлений и 92,47% строк. Из-за различий учёта async/greenlet этот отчёт не заменяет основной прогон `sys.monitoring` и порог покрытия строк. Результат CI на GitHub ещё не проверялся: workflow подготовлен локально, Git ведёт владелец проекта.

## Нагрузка

Сценарий: 100 workspace, 1 000 проектов, 100 000 задач; 80% GET-списков и 20% PATCH-задач. Docker Desktop, API ограничен 2 CPU / 2 GiB, PostgreSQL — 2 CPU / 4 GiB; клиент выполнялся на Windows. Во время основного прогона также проводилось учение backup/restore на тестовой БД.

| Показатель | Измерено | Цель |
| --- | --- | --- |
| Продолжительность | 600,03 с | 600 с |
| Частота | 50,00 запросов/с | 50 запросов/с |
| Всего запросов | 30 000 | 30 000 |
| p95 чтения | 35,68 мс | ≤ 300 мс |
| p95 записи | 36,59 мс | ≤ 500 мс |
| p99 чтения / записи | 170,92 / 168,33 мс | Информационно |
| HTTP 200 | 29 999 | — |
| HTTP 5xx | 0 | < 1% |
| Транспортные ошибки клиента | 1 (0,003%) | Учтены отдельно |

Для одного транспортного сбоя первоначальный драйвер не сохранил тип исключения, поэтому точная причина не установлена. В серверных логах ошибок нет; серверные счётчики показывают 29 999 обработанных запросов. Это согласуется со сбоем до обработки запроса приложением, но не доказывает конкретную причину. Драйвер дополнен классификацией HTTPX-исключений. Дополнительный 30-секундный прогон на 1 500 запросов прошёл без ошибок: p95 чтения 31,72 мс, записи 31,40 мс.

Исходные отчёты: [основной прогон](benchmark.json), [дополнительный прогон](benchmark-smoke.json). Результаты подтверждают указанный локальный профиль, а не производительность произвольного production-развёртывания или одного крупного workspace.

## Пароли и резервное копирование

Argon2id измерен отдельно, последовательно, в тестовом контейнере API с лимитом 2 CPU / 2 GiB: 20 образцов; p95 хеширования 120,01 мс, проверки 171,04 мс. Параметры: 65 536 KiB памяти, time cost 3, parallelism 4. В приложении конкурентность таких операций ограничена четырьмя. [Отчёт](auth-benchmark.json).

`pg_dump` и `pg_restore` проверены на 100 000 задачах в новой временной БД. Dump занял 0,965 с, restore — 2,129 с; совпали количества пользователей, workspace, проектов, задач, ролей и ревизия миграции. [Отчёт](backup-rehearsal.json). Production RPO/RTO и внешнее хранение копий этим учением не подтверждены.
