# Эксплуатация и восстановление

## Сборка и развёртывание

Соберите образ по `uv.lock`, выполните миграции единственным job-процессом и только затем обновляйте API. В текущем Compose этот порядок задают зависимости сервисов. Базовые образы Python, uv, PostgreSQL и Redis закреплены digest. Образ приложения имеет тег `0.1.0`; при релизе присваивайте отдельный неизменяемый тег или digest.

В production используйте HTTPS на reverse proxy, отдельные секреты, учётную запись БД с минимально необходимыми правами и явно заданные CORS origins. Расширение `pg_trgm` должно быть доступно миграционному пользователю; при ограниченных правах его предварительно устанавливает администратор БД. Swagger можно закрыть средствами прокси. `/metrics` и порты инфраструктуры должны оставаться во внутренней сети.

Readiness проверяет PostgreSQL и Redis с ограниченным временем ожидания; liveness не зависит от них. Redis используется для распределённого rate limit. При его недоступности защищённые API-маршруты дают `503`. Удаление членства действует сразу при последующей проверке прав, независимо от срока access-токена.

## Метрики

`/metrics` предоставляет текстовый формат Prometheus:

- `taskman_http_requests_total` по методу, шаблону маршрута и статусу;
- `taskman_http_duration_seconds` — histogram длительности;
- `taskman_db_connections_checked_out` и `taskman_db_pool_size` — состояние пула.

Ошибки зависимостей видны по `503`, ошибки приложения — по `5xx`. Неизвестные URL агрегируются под `unmatched`; идентификаторы объектов и строки запросов не попадают в labels. Для нескольких реплик метрики собираются с каждой отдельно, счётчики сбрасываются при рестарте процесса. JSON-логи содержат `request_id` и длительность; access-лог Uvicorn отключён, чтобы не записывать query-параметры.

## Резервные копии

Production-политика должна выполнять ежедневный `pg_dump --format=custom` или использовать managed backup PostgreSQL, хранить копии отдельно от сервера БД, шифровать их и ограничивать доступ. Для RPO меньше суток потребуется архивирование WAL/PITR. Срок хранения и внешний планировщик выбираются при развёртывании; текущий проект не устанавливает расписание на компьютере пользователя.

Восстанавливайте сначала в новую БД: создайте её, выполните `pg_restore --exit-on-error`, проверьте миграционную ревизию, связи и количество ключевых сущностей. Затем запустите API с восстановленной БД и выполните health- и бизнес-smoke-проверки. Переключение production-трафика выполняется отдельно; не восстанавливайте дамп поверх работающей БД без плана отката.

Локальное учение для выделенного тестового Compose:

```powershell
.\.venv\Scripts\python.exe scripts/backup_rehearsal.py
```

Скрипт использует только `compose.test.yaml` и `taskman_test`, создаёт уникальную временную БД, сравнивает количество пользователей, workspace, проектов, задач, ролей и ревизию миграций. После проверки удаляется только созданная им БД. Дамп остаётся в `/tmp` тестового контейнера до его удаления. Отчёт записывается в `docs/backup-rehearsal.json`.

Это проверка механизма dump/restore, а не доказательство production RPO/RTO. Цели RPO 24 часа и RTO 4 часа требуют учения на реальном объёме данных с выбранным внешним хранилищем перед релизом и затем ежеквартально.

## Откат

Миграции изменяются добавлением новых ревизий. Для несовместимого изменения используйте expand/contract. Откат API допустим только при совместимой схеме; автоматический разрушительный downgrade не заменяет резервную копию. Интеграционные тесты проверяют обновление начальной схемы до текущей и отсутствие расхождений с ORM.
